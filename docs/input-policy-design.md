# 输入策略层需求补充：五笔、全拼、双拼与词库优先级

日期：2026-11-05。状态：需求与设计建议，尚未修改输入引擎实现。

## 1. 需求结论

在现有 ImeEngine 的调用入口增加输入策略协调层，统一管理启用的输入方式、词库顺序、回退条件、固定顺序和个人词频。WPF 负责编辑配置，后台服务执行策略；TSF 继续负责按键、候选展示和宿主提交。

当前实现只有 Wubi86、Pinyin、Custom 三种 scheme；双拼仍是原设计的后续扩展。将双拼纳入此次交付，需要新增解码器和键位方案，不是仅添加一个设置项。

## 2. 分开输入方式与词库来源

| 维度 | 内容 | 含义 |
| --- | --- | --- |
| 输入方式 | 五笔、全拼、双拼 | 把用户按键解析成可检索编码/音节 |
| 词库来源 | 自定义词库、内置五笔库、内置拼音库、以后导入的词库 | 提供词条与编码映射 |
| 自定义快捷编码 | 如 `;dz`，也可显式绑定普通字母别名 | 用户定义的直接编码映射，独立于中文拆码 |

同一用户词条可以同时绑定五笔码、拼音码和快捷编码。双拼解码后复用拼音词库，避免复制一份“独立双拼词库”。双拼布局是输入方式配置的一部分，必须有稳定 layout_id。

当前 EntrySource 只有 User/Builtin，若要用户调整多个词库顺序，应增加稳定 dictionary_id/provider_id，不把枚举数值或显示名称当作长期身份。

## 3. 推荐的用户开关及默认值

| 设置 | 推荐默认 | 行为 |
| --- | --- | --- |
| 当前主要输入方式 | 沿用已有用户选择，首次沿用现有默认 | 混输关闭时只启用该解析器；用户词库仍参与 |
| 混输开关 | 默认关闭以保持现有行为，可由用户全局开启 | 开启后，在用户启用的五笔/全拼/双拼方式之间检索或回退 |
| 匹配策略 | 级联回退 | 按词库顺序寻找有效候选；首版优先实现该需求，完全合并混排可另行扩展 |
| 词库顺序 | 自定义词库 → 内置五笔库 → 内置拼音库 | 只参与当前启用解析器能够查询的来源，允许拖动、禁用和恢复默认 |
| 词频优先 | 开启 | 个人频次/衰减/近期加分参与同层候选排序 |
| 回退判定 | 先精确匹配，再补全 | 避免高优先词库的一条补全永久遮住下一词库的精确词 |

混输开关与词库优先级独立：混输关闭时，依然可以在当前输入方式下先查自定义词库，再查相应内置库。混输开启后，才允许跨其他输入解析方式回退。

“词频优先关闭”建议只冻结个人习惯对排序的影响，保留历史数据，并继续记录成功选词；重新开启后恢复原习惯。若用户还需要停止学习，应使用独立 learning_enabled 语义，避免一个开关含糊地兼管排名与数据删除。

关闭词频优先时，个人频次、衰减和近期使用加分均不参与排名；基础词典顺序、手工固定顺序仍可生效。不能只关频次项，却继续用近期加分让顺序跳动。

## 4. 级联匹配规则

推荐流程：

```text
按键组合 + 本次配置快照
        ↓
显式快捷编码 / 允许的五笔、全拼、双拼解析器
        ↓
按匹配质量与词库优先级检索
        ↓
候选去重 → 手工固定顺序 → 同层个人排序
        ↓
候选快照 → 用户选词 → 宿主成功确认 → 对实际来源学习
```

默认规则：

1. 先在精确匹配这一组中，按用户词库顺序查找。自定义库有精确候选时优先采用；没有则查下一兼容词库，以此类推。
2. 所有启用来源都没有精确候选时，再在完整音节前缀/补全组中按相同顺序查找。
3. 对同一词库中的多个解析结果，以当前主要输入方式及配置的解析顺序解决平局，不在输入中擅自改变主要模式。
4. 各层无结果时，保留组合串，由用户确认原码或取消，不自动选一个不相关词上屏。
5. 若优先词库有结果但用户不想选，提供“下一词库/更多来源”的显式入口；自动回退不把“用户还没确认”当作匹配失败。

例如高优先库仅有 `abcd` 的补全，而用户输入 `abc` 时，下一词库有 `abc` 的精确候选，推荐显示后者。如果用户需要严格“第一库只要有任何候选就停”，可以提供高级回退条件：完全无候选才回退；不要把两种规则混成不确定行为。

词库优先级建议用明确的拖动顺序，不在首版引入难解释的随机权重。默认个人高频词不能跨越手工设定的来源层级；如果以后提供跨库综合加权，必须作为另一种明确策略。

## 5. 手工排序与词库优先级的关系

用户显式固定的候选顺序优先于自动来源/词频策略，作用域为本输入配置与查询编码。协调层应先召回允许来源中合法的固定候选，再补当前优先层的普通候选；禁用的输入方式或词库不得因置顶而重新出现。

未固定候选按以下顺序处理：

```text
匹配质量 → 词库顺序 → 输入方式平局顺序 → 个人词频/基础词序 → 稳定 ID
```

词频关闭不删除置顶或手工名次。不同方案、双拼布局与查询编码的固定顺序不能互相覆盖。

同文候选来自多个来源时展示去重，但保留完整的来源轨迹；根据本次策略选定一个明确的学习归属，不把多条别名或多个来源的同一次选择重复累计。

## 6. “不能上屏”的两类情况必须分开

- **检索没有有效匹配**：可以自动回退到下一兼容词库/解析器。
- **用户已选词，但宿主只读、编辑会话失败或服务确认失败**：保持原选择身份，执行 Stage 3 的取消、恢复或确认重试。不得改用下一词库的另一个词重试插入。

无匹配、解析器不适用与词库读取错误也要分别表示。词库加载/数据库错误不能静默伪装为无匹配；保留明确的降级状态或手动选择来源，避免故障时突然插入另一种含义的词。

## 7. 策略快照与学习身份

新组合开始时锁定 policy_revision，组合期间的普通设置变更在下一组合生效。已经发出的候选与选词事件不重新按新优先级解释；如果需要立即应用，显式取消/刷新组合并保留既有未决提交。

候选及持久化事件需要能追溯：

- 实际 input_method、双拼 layout_id。
- 用户实际输入 raw_code，以及用于词库查找的 resolved_code/音节。
- dictionary_id、稳定 entry_id。
- policy_revision、词库 revision 和候选快照身份。

上述信息主要保存在服务端候选/事件快照，TSF 未必需要携带所有字符串。优先沿用稳定快照/候选 token，确需改变帧结构时升级协议并同步两端测试。

双拼与全拼可以共享词条，但不应把不同布局的原始输入统计混在同一个键下。学习按本次实际选中的路线归属，布局/优先级变化不清空已有习惯；数据模型扩展需真实迁移，保留旧方案统计与回执。

## 8. 对现有工程的影响

| 模块 | 影响 | 具体内容 |
| --- | --- | --- |
| ime-core | 较大 | 引入输入策略协调层、双拼解码器、词库来源身份、级联检索和可配置排序 |
| SQLite/备份 | 中等 | 策略与布局配置、来源/学习键迁移、固定顺序作用域；备份完整往返 |
| ime-service | 中等 | 执行查询策略快照，保持候选/事件原始来源，限制多解析器总耗时 |
| TSF/IPC | 中等 | 保持提交恢复链路，展示/选择有效快照，可选来源标签；避免改动宿主提交规则 |
| Admin IPC | 中等 | Get/SaveInputPolicy、词库启用/顺序、双拼布局及排序上下文接口 |
| WPF | 中等 | 全局开关、启用方式、双拼方案、拖动词库顺序及可解释候选来源 |

现有核心不能仅靠外部拼接几次 Query 得到正确结果：Ranker 目前的用户/内置词合并会改变候选 ID 并组合统计，尚无多词库路线身份；服务也按一个 scheme 查询。需要在核心入口统一模型，不能把这些规则复制到 WPF。

多解析器必须共享单次查询的总预算，不能每种方式各花一份完整按键超时。延迟隔离与管理操作保护继续遵循 Stage 4 设计审阅要求。

## 9. Stage 4 范围调整与实施顺序

建议在当前 Stage 4 设计冻结前纳入该补充，分为：

1. **Stage 4A 输入策略**：完成规则与配置 schema；先在 CLI/无头服务中验证自定义优先、级联回退和词频开关；实现双拼时先确定键位方案与稳定布局 ID。
2. **Stage 4B 管理接口**：通过 Admin IPC 配置策略、词库顺序、固定排序与词库内容，保持单一服务数据所有权及未决事件保护。
3. **Stage 4C WPF**：绑定已经验证的策略接口，交付开关和词库优先级编辑器。

验收应至少覆盖：混输关闭隔离、开启后跨方式回退、自定义精确优先、补全不遮挡下一库精确候选、词频关闭排名稳定、手工名次不受影响、双拼布局隔离、同文多来源一次学习、组合中改设置、已有候选/未决事件经历策略变更、空结果和资源故障的不同处理。

这是需求扩展，不否定已完成的 Stage 3 传输与提交恢复实现。WPF 原规划需先按新能力模型修订，再继续编码。
