# Stage 3 回执日志：最终收尾实现

本说明替代 stage3-design 中 Round 3–10 的共享文件压缩与析构保底方案。旧轮次的测试输出是历史证据，不是当前实现的完整验收结论。

## 当前契约

- 每个来源事件的 session/context/event/action 不可变。
- 收到服务端候选后、请求宿主编辑前，写 P1 意图帧并物理提交；失败时不请求宿主编辑。
- 宿主返回实际结果后，先提交 R1 结果帧，再发送 CommitSuccess/CommitCancel。入队返回 bool，失败不伪装 persisted。
- R1 提交失败时由独立于 TIP 的模块级重试所有者接管，阻止当前模块继续发起新的宿主编辑；持有模块引用直到接管结果落盘。TIP 析构不无锁写共用文件。
- 服务端确认后追加 A1 墓碑，ACK 写入失败保留重试。ACK 对所有历史/未来重复 R1 均为终态；重放服务端终态本身幂等，不重复学习。
- 正常新日志只有 PersonalIME_receipts.wal，一个 mutex 覆盖读取及追加。没有压缩、重命名、轮转或中间文件。

## 格式与恢复

完整行格式：`R1 sid cid eid action retry checksum`、`A1 eid checksum`、`P1 sid cid eid action retry checksum`。checksum 为行正文的 FNV-1a 64 位校验，检测不完整/损坏帧，不用于身份认证。

每次追加从换行开始并在结尾换行，检查 fwrite/fflush/_commit/fclose。所有写者必须获得同一 Windows 命名 mutex，不能仅依赖 stdio append 自称跨进程原子。

恢复先读所有有效帧，再对所有来源统一应用 ACK 集合，ACK 后出现的旧 REC 不能复活事件。P1 仅为意图，绝不能作为宿主插入成功的证据。读取 SQL/文件错误与空集合分离；不完整尾部或校验失败帧发出诊断并跳过，前序完整帧保留。

旧主/紧急日志及其所有后缀文件作为只读迁移来源，读取时遵守原锁域。不会删除唯一旧副本，也不会产生新 `.tmp/.swap/.bak`。新日志 ACK 全局覆盖这些来源。四字段旧记录缺少稳定 sid，不能使用当前 TIP 冒领；保留源文件并诊断，需人工或基于服务端原始归属恢复。

## 保证边界

此文件日志是 write-ahead/outcome journal，不是 SQLite WAL。它保护已成功提交的结果及终态，并提供锁争用/暂时磁盘故障后跨 TIP 的重试交接。

宿主文档、客户端磁盘与服务端 SQLite 不属于同一事务。若宿主已修改，但 R1 尚未提交且整个宿主进程崩溃，只有 P1/服务端 pending 可以证明存在未决意图，不能自动推断 Success 或 Cancel。本实现不承诺该窗口的“100%自动学习/零丢失”；模块级内存接管也不能冒充进程崩溃持久化。任意存储永久失败、OS无法创建重试线程也属于明确的降级，不得继续宣称全失败模型已闭环。

日志按约定不压缩，因此磁盘占用与全量扫描时间会增长；每轮最多 8 次服务端通知不意味着全量恢复扫描总耗时也有硬上限。大规模日志索引/配额需要后续单独设计，不能通过删除未决结果限流。
